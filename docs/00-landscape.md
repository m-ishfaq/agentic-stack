# 00. Landscape

Research checked November 2026. Claims about adoption come from the sources named, not from memory.

## The short version

- `AGENTS.md` is the cross-tool standard. Use it as the root.
- Every other tool file is an adapter, generated from one source.
- Skills (`SKILL.md`) are the portable way to ship procedures.
- Hooks exist only in some tools. CI is the only portable enforcement.
- Nobody ships the full package we want: safety policy, project scope, safe test database, and a response contract in one install.

The practical reading: a root `AGENTS.md` is now table stakes for a serious repo. The differentiator is not the file, it is what the file can enforce.

Design consequences:

1. `AGENTS.md` must be the root of truth, not `CLAUDE.md`.
2. `CLAUDE.md` contains `@AGENTS.md` plus Claude-only notes. Do not duplicate rules.
3. Cursor needs `.mdc` files with frontmatter because plain `.md` in that folder is ignored.
4. Copilot needs the instructions file for IDE chat, even though the agent reads `AGENTS.md`.
5. Any hook we ship is an accelerator. CI must run the same checks.

## Skills

`SKILL.md` is an open standard, published December 2025 and now read by 46 tools.

```text
skill-name/
  SKILL.md          required: YAML name and description, then Markdown
  scripts/          optional executables
  references/       optional docs loaded on demand
  assets/           optional templates
```

The cross-client location is `.agents/skills/<name>/SKILL.md`. Tool-specific folders still work and are generated by symlink or copy when needed.

Skill budget per description: 1,024 characters. Keep the description about *when* to use it, not *what* it contains.

## Prior art

| Project | What it does | What it does not do |
|---|---|---|
| `rulesync` | converts rules, skills, subagents, hooks, permissions between 30+ tools | no safety policy, no project scope, no safe test database |
| `ruler` | concatenates Markdown rules to many agent files | rules only |
| `agentsync` | one source for rules, skills, MCP across many tools | no enforcement model |
| `spec-kit` | spec-driven workflow, templates, CLI | no hooks, no policy, no adapters for every tool |
| `claude-code-templates` | registry and installer for Claude components | Claude-only, no portable baseline |
| `agent-starter` | skills, hooks, templates, self-improvement loop | Claude-centric, no stack neutrality |
| `agentic-templates/repo-template` | issue to PR autonomous repo | not an installer, no policy layer |
| `agents-md-templates` | copy-paste instruction templates | templates only, no sync or upgrade |

## The gap we fill

Existing tools optimize for one of three things: converting formats, shipping prompts, or automating a workflow. None of them ship the parts that make an agent safe to leave unattended:

- a deny-by-default policy that is generated for each tool and re-checked in CI
- a project boundary that blocks paths outside the installed repo
- test isolation that makes it impossible to wipe the developer database
- a response contract that controls how the agent communicates, not just what it writes
- an upgrade path that does not overwrite local edits

That is the product. The adapters are commodity; the policy and the contract are not.

## What we borrow

- `AGENTS.md` as the root file.
- `.agents/skills/` as the skill location.
- `.mdc` frontmatter for Cursor rules.
- `applyTo` frontmatter for Copilot path instructions.
- The lockfile and 3-way merge idea from package managers.
- The deny, ask, allow split from permission systems.

## What we refuse

- A vendor-specific root file.
- Bash-only hooks. Windows is a first-class target.
- Rules longer than the agent will read. Always-on budget is about 2k tokens.
- Copy-paste duplication between tool files.
- Silent overwrites on upgrade.
- Telemetry.
